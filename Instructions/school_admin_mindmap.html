Multi-Tenant Platform Architecture

RBAC Permission Model

Use Hierarchical RBAC (HRBAC), not flat RBAC — permissions inherit down the org chart (Super Admin → Director → Principal → Dept Heads → Staff), which mirrors how real schools work and keeps admin effort low as you onboard more tenants.

Permission = (Role × Module × Action × Scope). Action ∈ {view, create, edit, delete, approve, export, assign}. Scope ∈ {own, department, school, group-of-schools, platform}. Store as a role_permissions table so Directors can build custom roles per school without touching code (e.g. "Front Office Coordinator" = Admin module minus Finance).

Enforce it twice: (1) Postgres Row-Level-Security in Supabase, keyed off auth.uid() → staff.user_id → staff.school_id/role_id so even a leaked API key can't leak cross-tenant data; (2) FastAPI dependency (Depends(require_permission("finance.fee.collect"))) that checks a cached permission set from Redis/Supabase for fast, explicit checks at the route layer. Never trust the Flutter client for authorization — it only hides UI it can't use.
